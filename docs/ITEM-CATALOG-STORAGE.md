## Contract and persistence

- Migration `20261022090000_item_catalog_details` adds nullable Item.description and Item.photoKey. Existing rows stay valid; no data reset/backfill is needed. Name normalization/uniqueness and role permissions are unchanged. Creation does not add units.
- Additive migration `20261026060000_item_catalog_multiple_photos` creates ItemPhoto with stable UUID, item relation, unique storage key, unique per-item position and timestamp. The itemId/position index also covers the foreign key. It backfills every existing non-null cover as position0, retaining the file/key and original item creation time. Item.photoKey remains the first-photo cover pointer for existing clients; creation writes it and all gallery metadata in one transaction. No column/file is dropped. Migration is authored, not yet executed by the agent.
- POST /api/items accepts the existing application/json body (name, optional description) and new multipart/form-data (name, optional description/photo). Origin validation and inventory:item:create authorization run before body parsing. Other mutation endpoints remain JSON-only by default.
- Name remains 1–100 characters; description trims and permits up to 2000 characters. Empty description becomes null. Duplicate name/description fields, unknown fields and non-file photo entries are rejected. Repeated `photo` file fields preserve selection order. JSON keeps its256KiB limit; catalog multipart is bounded to16MiB including framing/text while streaming before form parsing. Technical limits are0–10 catalog photos,2MiB per file; callers may hit the total byte cap before10 files. A zero-byte browser placeholder with no filename is ignored for old forms without a photo; named empty files are rejected.
- Catalog file limit 2 MiB, static JPEG/PNG/WebP only, maximum decoded input 20 million pixels. Signature is checked independently of supplied MIME/name. Sharp decodes, applies orientation, shrinks inside 1600×1600 without enlarging, and re-encodes WebP85 without preserving EXIF. Corrupt, SVG, animated and oversized inputs are rejected.
- Sharp 0.35.5 was already installed as Next's dependency; it is now declared directly in package.json/lockfile. No package version was downloaded/upgraded. npm ls sharp verifies a deduped installation. Offline lock normalization hit unavailable npm artifacts; required flags for its existing dependency entries were updated locally.
- Files use generated UUID.webp keys, never browser paths/names. Default root is .data/item-photos under project cwd; ITEM_PHOTO_DIR can select an absolute persistent directory. Tests always use .data/test-item-photos, ignoring the production override. .data is excluded from Git.
- All files are validated/re-encoded before staging. Files are then written before one Item/ItemPhoto/audit transaction. Staging failure or known rollback removes this attempt's staged files; an uncertain COMMIT preserves files that may be referenced. A process crash or uncertain result can leave an unreferenced private file. Filesystem and Postgres are not a distributed atomic transaction; no automatic destructive orphan cleanup has been added.
- ITEM_CREATED audit records description, cover key and ordered photo keys/IDs. PATCH existing item still edits name/description only; appending, deleting, replacing or reordering persisted catalog photos is outside this slice. Unit-photo history is unchanged.

## Reads and access

POST /api/items, GET /api/items and GET /api/items/[itemId]/units retain description/photoUrl and add ordered `photos: [{ id, position, url }]`. Empty galleries return an empty array. They do not expose storage keys/paths. GET /api/items/[itemId]/photo keeps the existing first-photo cover URL; GET /api/items/[itemId]/photos/[photoId] resolves a specific gallery photo and checks that it belongs to that item. Both require active-user inventory:view and use the shared private,no-store image/webp response with nosniff/restrictive CSP. Missing item/photo/file returns404. Management may read; System Admin alone has no inventory permission. No publicly accessible static upload folder is created.

Frontend uses next/image unoptimized so browser cookies reach the authorized endpoint; the Next image optimizer must not fetch a private photo without that session. Placeholder remains for items without a photo. Actual images render in the 144px card area and selected-item panel; description appears in that panel.

## Deployment and backups

Deploy on a server with durable writable disk, retaining ITEM_PHOTO_DIR across releases/container recreation. Back up that directory alongside the database so keys and files remain consistent. Restrict directory access to the app/service account; Windows ACLs must be configured by the deployer. Local disk is not a serverless/multi-instance storage solution. A later deployment requiring those environments needs an explicitly selected shared/object storage migration.

After pulling this schema change elsewhere, run db:generate and db:migrate; restart an existing dev server so its global Prisma singleton reloads the new client.
